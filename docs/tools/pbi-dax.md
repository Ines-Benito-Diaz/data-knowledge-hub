# Power BI DAX Cheat Sheet
**Advanced DAX | Power BI | Data Analytics | Business Intelligence**

---

## 1. DAX Fundamentals

DAX (Data Analysis Expressions) is the formula language used in Power BI, Analysis Services and Power Pivot.

It is primarily used to create:
- Measures: Dynamic calculations evaluated according to filter context.
- Calculated columns: Row-level calculations stored in the data model.
- Calculated tables: Tables generated through DAX expressions.

### Basic syntax

```dax
Measure Name =
    CALCULATE(
        SUM(Sales[Revenue]),
        Sales[Status] = "Completed"
    )
```

### DAX naming conventions

| Element | Example |
|---|---|
| Measures | `[Total Revenue]` |
| Calculated columns | `Customers[Customer Segment]` |
| Tables | `Sales`, `Customers`, `Calendar` |
| Variables | `VAR TotalSales` |
| Functions | `CALCULATE()`, `SUMX()` |

### Calculated Columns vs Measures vs Calculated Tables

| Feature | Calculated Column | Measure | Calculated Table |
|---|---|---|---|
| Evaluation | Row by row | On demand | During model processing |
| Storage | Stored in model | Formula only | Stored in model |
| Responds to filters | No, values are precomputed | Yes | No, table is precomputed |
| Typical use | Categories, flags, keys | KPIs, ratios, aggregations | Date tables, intermediate models |
| Performance impact | Increases model size | Depends on query complexity | Increases model size |

**Best practice:** Prefer measures for analytical calculations that need to respond dynamically to report filters.

## 2. Evaluation Context

Understanding evaluation context is fundamental to writing advanced DAX.

### Row Context

Row context refers to the current row being evaluated.

Commonly exists in:
- Calculated columns.
- Iterator functions such as `SUMX()`, `FILTER()` and `ADDCOLUMNS()`.

Example:

```dax
Line Revenue =
    Sales[Quantity] * Sales[Unit Price]
```

Each row calculates its own revenue.

### Filter Context

Filter context determines which rows are visible to a calculation.

It can be generated by:
- Report filters.
- Page filters.
- Visual-level filters.
- Slicers.
- Rows and columns in a visual.
- DAX functions such as `CALCULATE()`.

Example:

```dax
Total Revenue =
    SUM(Sales[Revenue])
```

If a report is filtered by country, the measure calculates revenue only for that country.

### Context Transition

Context transition occurs when `CALCULATE()` or `CALCULATETABLE()` transforms an existing row context into filter context.

```dax
Customer Revenue =
    SUMX(
        VALUES(Customers[Customer ID]),
        CALCULATE(
            SUM(Sales[Revenue])
        )
    )
```

Here:
1. `VALUES()` returns the distinct customers.
2. `SUMX()` iterates over each customer.
3. `CALCULATE()` transforms the current row context into filter context.
4. Revenue is calculated for the current customer.

**Important:** Context transition is one of the most important concepts when working with nested iterators and complex measures.

### Evaluation context summary

| Context | Description | Common functions |
|---|---|---|
| Row context | Current row being evaluated | `SUMX()`, `FILTER()` |
| Filter context | Filters affecting a calculation | `CALCULATE()`, `ALL()` |
| Context transition | Converts row context into filter context | `CALCULATE()` |

## 3. Variables — VAR / RETURN

Variables improve readability, reduce repeated calculations and make debugging easier.

### Basic syntax

```dax
Measure =
VAR TotalSales =
    SUM(Sales[Revenue])

VAR TotalCosts =
    SUM(Sales[Cost])

RETURN
    TotalSales - TotalCosts
```

### Multiple variables

```dax
Profit Margin =
VAR Revenue =
    SUM(Sales[Revenue])

VAR Costs =
    SUM(Sales[Cost])

VAR Profit =
    Revenue - Costs

RETURN
    DIVIDE(Profit, Revenue, 0)
```

### Variables with conditions

```dax
Customer Classification =
VAR Revenue =
    [Total Revenue]

RETURN
    SWITCH(
        TRUE(),
        Revenue >= 100000, "High Value",
        Revenue >= 50000, "Medium Value",
        Revenue > 0, "Low Value",
        "No Revenue"
    )
```

### Variables for debugging

```dax
Debug Measure =
VAR TotalSales =
    [Total Revenue]

VAR TotalCustomers =
    [Total Customers]

VAR AverageRevenue =
    DIVIDE(TotalSales, TotalCustomers)

RETURN
    AverageRevenue
```

**Best practices:**
- Use descriptive variable names.
- Define repeated calculations once.
- Use variables to simplify nested expressions.
- Remember that variables are evaluated in the context where they are defined. They are not recalculated simply because a later `CALCULATE()` changes the filter context.

## 4. Basic Aggregation Functions

| Function | Purpose |
|---|---|
| `SUM()` | Sum a numeric column |
| `AVERAGE()` | Calculate arithmetic mean |
| `MIN()` | Minimum value |
| `MAX()` | Maximum value |
| `COUNT()` | Count non-blank numeric values |
| `COUNTA()` | Count non-blank values |
| `COUNTROWS()` | Count rows in a table |
| `DISTINCTCOUNT()` | Count unique values |
| `PRODUCT()` | Multiply values in a column |

### Examples

```dax
Total Revenue =
    SUM(Sales[Revenue])
```

```dax
Average Revenue =
    AVERAGE(Sales[Revenue])
```

```dax
Total Transactions =
    COUNTROWS(Sales)
```

```dax
Unique Customers =
    DISTINCTCOUNT(Sales[Customer ID])
```

```dax
Average Order Value =
    DIVIDE(
        [Total Revenue],
        [Total Transactions]
    )
```

**Important:** `COUNT()` only counts non-blank numeric values. Use `COUNTA()` for non-blank values of other types.

## 5. Iterator Functions (X Functions)

Iterator functions evaluate an expression row by row and then aggregate the results.

They are especially useful when calculations cannot be performed directly on a single column.

### SUMX()

```dax
Total Revenue =
    SUMX(
        Sales,
        Sales[Quantity] * Sales[Unit Price]
    )
```

### AVERAGEX()

```dax
Average Customer Revenue =
    AVERAGEX(
        VALUES(Customers[Customer ID]),
        [Total Revenue]
    )
```

### COUNTX()

```dax
Customers With Revenue =
    COUNTX(
        VALUES(Customers[Customer ID]),
        [Total Revenue]
    )
```

### MAXX() / MINX()

```dax
Highest Transaction =
    MAXX(
        Sales,
        Sales[Quantity] * Sales[Unit Price]
    )
```

### CONCATENATEX()

```dax
Customer List =
    CONCATENATEX(
        VALUES(Customers[Customer Name]),
        Customers[Customer Name],
        ", ",
        Customers[Customer Name],
        ASC
    )
```

### Common iterator functions

| Function | Purpose |
|---|---|
| `SUMX()` | Sum evaluated expressions |
| `AVERAGEX()` | Average evaluated expressions |
| `COUNTX()` | Count non-blank evaluated expressions |
| `MAXX()` | Maximum evaluated expression |
| `MINX()` | Minimum evaluated expression |
| `RANKX()` | Rank an expression |
| `CONCATENATEX()` | Concatenate evaluated text |
| `PRODUCTX()` | Multiply evaluated expressions |

**SUM vs SUMX**

```dax
-- Direct aggregation
SUM(Sales[Revenue])

-- Row-level calculation followed by aggregation
SUMX(
    Sales,
    Sales[Quantity] * Sales[Unit Price]
)
```

Use `SUM()` when the required values already exist in a column. Use `SUMX()` when you need to calculate something for each row before aggregating.

## 6. CALCULATE() — Filter Context Manipulation

`CALCULATE()` is arguably the most important function in DAX.

It evaluates an expression under a modified filter context.

### Basic syntax

```dax
CALCULATE(
    <expression>,
    <filter1>,
    <filter2>,
    ...
)
```

### Apply a filter

```dax
Completed Revenue =
    CALCULATE(
        [Total Revenue],
        Sales[Status] = "Completed"
    )
```

### Multiple filters

```dax
Spain Revenue =
    CALCULATE(
        [Total Revenue],
        Sales[Country] = "Spain",
        Sales[Status] = "Completed"
    )
```

### Remove existing filters

```dax
Total Revenue All Countries =
    CALCULATE(
        [Total Revenue],
        REMOVEFILTERS(Customers[Country])
    )
```

### Override existing filters

```dax
Online Revenue =
    CALCULATE(
        [Total Revenue],
        Sales[Channel] = "Online"
    )
```

A Boolean filter argument normally replaces an existing filter on the same column, rather than intersecting with it.

Use `KEEPFILTERS()` when intersection is required.

### CALCULATE vs CALCULATETABLE

| Function | Returns |
|---|---|
| `CALCULATE()` | A scalar expression |
| `CALCULATETABLE()` | A table expression |

```dax
High Value Sales =
    CALCULATETABLE(
        Sales,
        Sales[Revenue] > 1000
    )
```

## 7. Filter Manipulation Functions

These functions control which filters affect a calculation.

### ALL()

Removes filters from a table or column and returns an unfiltered table.

```dax
Total Revenue All Products =
    CALCULATE(
        [Total Revenue],
        ALL(Products)
    )
```

### REMOVEFILTERS()

Explicitly removes filters.

```dax
Revenue Without Country Filter =
    CALCULATE(
        [Total Revenue],
        REMOVEFILTERS(Customers[Country])
    )
```

### ALLEXCEPT()

Removes all filters from a table except specified columns.

```dax
Revenue By Country =
    CALCULATE(
        [Total Revenue],
        ALLEXCEPT(
            Customers,
            Customers[Country]
        )
    )
```

### ALLSELECTED()

Removes visual-level row and column filters while retaining relevant external selections, making it useful for visual totals.

```dax
Revenue % of Selected Total =
    DIVIDE(
        [Total Revenue],
        CALCULATE(
            [Total Revenue],
            ALLSELECTED(Products[Category])
        )
    )
```

### KEEPFILTERS()

Intersects a new filter with existing filters instead of replacing them.

```dax
High Revenue Within Selection =
    CALCULATE(
        [Total Revenue],
        KEEPFILTERS(Sales[Revenue] > 1000)
    )
```

### FILTER()

Returns a filtered table.

```dax
High Value Revenue =
    CALCULATE(
        [Total Revenue],
        FILTER(
            Sales,
            Sales[Revenue] > 1000
        )
    )
```

### Filter function comparison

| Function | Main purpose |
|---|---|
| `ALL()` | Remove filters and return an unfiltered table |
| `REMOVEFILTERS()` | Remove filters |
| `ALLEXCEPT()` | Remove all filters except specified columns |
| `ALLSELECTED()` | Calculate relative to selected visual totals |
| `KEEPFILTERS()` | Intersect filters |
| `FILTER()` | Return rows meeting a condition |
| `VALUES()` | Return distinct visible values |
| `DISTINCT()` | Return distinct values from a column |

**Important:** These functions are not interchangeable. Their behavior depends on filter context, relationships and the structure of the data model.

## 8. Relationships & Filter Propagation

DAX can manipulate how relationships behave during calculations.

### RELATED()

Retrieve a value from the one-side of an existing relationship, typically in a calculated column.

```dax
Product Category =
    RELATED(Products[Category])
```

### RELATEDTABLE()

Retrieve related rows from the many-side.

```dax
Customer Order Count =
    COUNTROWS(
        RELATEDTABLE(Sales)
    )
```

### USERELATIONSHIP()

Activate an inactive relationship for a specific calculation.

Example: A sales table has Order Date and Delivery Date, with only Order Date actively connected to the calendar.

```dax
Revenue by Delivery Date =
    CALCULATE(
        [Total Revenue],
        USERELATIONSHIP(
            Sales[Delivery Date],
            Calendar[Date]
        )
    )
```

### CROSSFILTER()

Change the filter direction of an existing relationship for a calculation.

```dax
Revenue Bidirectional =
    CALCULATE(
        [Total Revenue],
        CROSSFILTER(
            Customers[Customer ID],
            Sales[Customer ID],
            BOTH
        )
    )
```

### TREATAS()

Apply values from one table as filters to unrelated columns.

```dax
Revenue Selected Products =
    CALCULATE(
        [Total Revenue],
        TREATAS(
            VALUES(ProductSelector[Product ID]),
            Products[Product ID]
        )
    )
```

### Relationship functions summary

| Function | Purpose |
|---|---|
| `RELATED()` | Retrieve a related scalar value |
| `RELATEDTABLE()` | Return related rows |
| `USERELATIONSHIP()` | Activate an inactive relationship |
| `CROSSFILTER()` | Change relationship filter direction |
| `TREATAS()` | Apply values as filters to another table |

## 9. Conditional Logic

### IF()

```dax
Revenue Status =
    IF(
        [Total Revenue] > 10000,
        "Target Achieved",
        "Below Target"
    )
```

### SWITCH()

```dax
Performance Category =
    SWITCH(
        TRUE(),
        [Achievement %] >= 1.2, "Excellent",
        [Achievement %] >= 1.0, "On Target",
        [Achievement %] >= 0.8, "Below Target",
        "Critical"
    )
```

### IFERROR()

```dax
Safe Calculation =
    IFERROR(
        [Total Revenue] / [Total Costs],
        BLANK()
    )
```

### COALESCE()

Returns the first non-blank expression.

```dax
Revenue Display =
    COALESCE(
        [Total Revenue],
        0
    )
```

### BLANK()

```dax
Revenue Measure =
    IF(
        [Total Revenue] = 0,
        BLANK(),
        [Total Revenue]
    )
```

**Best practice:** Prefer `DIVIDE()` over `/` when calculating ratios, as it handles division by zero safely.

## 10. Time Intelligence

Time intelligence functions calculate metrics across different time periods.

**Prerequisites:**
- A dedicated calendar table.
- A continuous date range without missing dates.
- A date column with unique values and no blank dates.
- The calendar table should be marked as a date table in Power BI.
- Appropriate relationships between the calendar and fact tables.

### Total Revenue

```dax
Total Revenue =
    SUM(Sales[Revenue])
```

### Year-to-Date (YTD)

```dax
Revenue YTD =
    TOTALYTD(
        [Total Revenue],
        Calendar[Date]
    )
```

### Quarter-to-Date (QTD)

```dax
Revenue QTD =
    TOTALQTD(
        [Total Revenue],
        Calendar[Date]
    )
```

### Month-to-Date (MTD)

```dax
Revenue MTD =
    TOTALMTD(
        [Total Revenue],
        Calendar[Date]
    )
```

### Previous Year

```dax
Revenue Previous Year =
    CALCULATE(
        [Total Revenue],
        SAMEPERIODLASTYEAR(Calendar[Date])
    )
```

### Previous Month

```dax
Revenue Previous Month =
    CALCULATE(
        [Total Revenue],
        DATEADD(
            Calendar[Date],
            -1,
            MONTH
        )
    )
```

### Year-over-Year (YoY)

```dax
Revenue YoY =
    [Total Revenue] - [Revenue Previous Year]
```

### YoY Growth %

```dax
Revenue YoY % =
    DIVIDE(
        [Revenue YoY],
        [Revenue Previous Year]
    )
```

### Month-over-Month (MoM)

```dax
Revenue MoM =
    [Total Revenue] - [Revenue Previous Month]
```

### MoM Growth %

```dax
Revenue MoM % =
    DIVIDE(
        [Revenue MoM],
        [Revenue Previous Month]
    )
```

### Rolling 12 Months

```dax
Revenue Rolling 12M =
VAR LastVisibleDate =
    MAX(Calendar[Date])

RETURN
    CALCULATE(
        [Total Revenue],
        DATESINPERIOD(
            Calendar[Date],
            LastVisibleDate,
            -12,
            MONTH
        )
    )
```

### Rolling 30 Days

```dax
Revenue Rolling 30D =
VAR LastVisibleDate =
    MAX(Calendar[Date])

RETURN
    CALCULATE(
        [Total Revenue],
        DATESINPERIOD(
            Calendar[Date],
            LastVisibleDate,
            -30,
            DAY
        )
    )
```

### Time intelligence reference

| Function | Purpose |
|---|---|
| `TOTALYTD()` | Year-to-date |
| `TOTALQTD()` | Quarter-to-date |
| `TOTALMTD()` | Month-to-date |
| `SAMEPERIODLASTYEAR()` | Equivalent previous-year period |
| `DATEADD()` | Shift date context |
| `DATESYTD()` | Return YTD dates |
| `DATESMTD()` | Return MTD dates |
| `DATESQTD()` | Return QTD dates |
| `DATESINPERIOD()` | Return a rolling date range |
| `PARALLELPERIOD()` | Shift by complete periods |

**Important:** Time intelligence results depend on the calendar table, filter context and date selection. Validate partial-period comparisons carefully.

## 11. Ranking & Top N Analysis

### RANKX()

```dax
Customer Ranking =
    RANKX(
        ALL(Customers[Customer Name]),
        [Total Revenue],
        ,
        DESC,
        DENSE
    )
```

### Rank within a selected context

```dax
Product Ranking =
    RANKX(
        ALLSELECTED(Products[Product Name]),
        [Total Revenue],
        ,
        DESC,
        DENSE
    )
```

### Top 10 Customers

```dax
Top 10 Customers Revenue =
VAR TopCustomers =
    TOPN(
        10,
        ALL(Customers[Customer ID]),
        [Total Revenue],
        DESC,
        Customers[Customer ID],
        ASC
    )

RETURN
    CALCULATE(
        [Total Revenue],
        KEEPFILTERS(TopCustomers)
    )
```

The secondary sort key makes the selection deterministic when revenue values are tied.

### Dynamic Top N

```dax
Dynamic Top N Revenue =
VAR SelectedN =
    SELECTEDVALUE(TopNParameter[Value], 10)

VAR TopCustomers =
    TOPN(
        SelectedN,
        ALLSELECTED(Customers[Customer ID]),
        [Total Revenue],
        DESC
    )

RETURN
    CALCULATE(
        [Total Revenue],
        KEEPFILTERS(TopCustomers)
    )
```

## 12. Virtual Tables & Table Functions

Virtual tables are temporary table expressions created during measure evaluation. They are not stored in the model.

### VALUES()

Returns distinct values in the current filter context.

```dax
Visible Customers =
    COUNTROWS(
        VALUES(Customers[Customer ID])
    )
```

### DISTINCT()

Returns distinct values from a column or table.

```dax
Unique Products =
    DISTINCT(Products[Product ID])
```

### SUMMARIZE()

Groups data by specified columns.

```dax
Customer Summary =
    SUMMARIZE(
        Sales,
        Sales[Customer ID],
        "Total Revenue", SUM(Sales[Revenue])
    )
```

### SUMMARIZECOLUMNS()

Creates a grouped table and evaluates expressions.

```dax
Sales Summary =
    SUMMARIZECOLUMNS(
        Customers[Country],
        Products[Category],
        "Revenue", [Total Revenue],
        "Orders", [Total Orders]
    )
```

### ADDCOLUMNS()

Adds calculated columns to a table expression.

```dax
Customer Analysis =
    ADDCOLUMNS(
        VALUES(Customers[Customer ID]),
        "Revenue", [Total Revenue],
        "Orders", [Total Orders]
    )
```

### SELECTCOLUMNS()

Creates a table with selected or renamed columns.

```dax
Customer Selection =
    SELECTCOLUMNS(
        Customers,
        "ID", Customers[Customer ID],
        "Name", Customers[Customer Name]
    )
```

### CROSSJOIN()

Creates all combinations of rows from two tables.

```dax
Product Country Matrix =
    CROSSJOIN(
        VALUES(Products[Category]),
        VALUES(Customers[Country])
    )
```

### GENERATE()

Evaluates a table expression for every row of another table.

```dax
Customer Products =
    GENERATE(
        VALUES(Customers[Customer ID]),
        VALUES(Sales[Product ID])
    )
```

### EXCEPT() / INTERSECT()

```dax
New Customers =
    EXCEPT(
        CurrentCustomers,
        PreviousCustomers
    )
```

```dax
Returning Customers =
    INTERSECT(
        CurrentCustomers,
        PreviousCustomers
    )
```

### Common table functions

| Function | Purpose |
|---|---|
| `VALUES()` | Distinct values in current context |
| `DISTINCT()` | Return distinct rows or values |
| `FILTER()` | Filter a table |
| `SUMMARIZE()` | Group and aggregate |
| `SUMMARIZECOLUMNS()` | Create grouped result tables |
| `ADDCOLUMNS()` | Add calculated columns |
| `SELECTCOLUMNS()` | Select and rename columns |
| `CROSSJOIN()` | Cartesian product |
| `GENERATE()` | Evaluate a table per row |
| `TOPN()` | Return top N rows |
| `EXCEPT()` | Return rows in first table only |
| `INTERSECT()` | Return common rows |
| `UNION()` | Combine tables |

```dax
Revenue % of Total =

```


```dax

```

```dax

    TRUE(),

    "Critical"
```

### Variance vs Target

```dax

    [Total Revenue] - [Revenue Target]
```

```dax

    DIVIDE(
        [Revenue Variance],
        [Revenue Target]
    )
```

### Dynamic Measure Selection

Use a disconnected selector table and `SWITCH()` to allow users to change the metric displayed in a visual.

```dax
Selected Metric =
SWITCH(
    SELECTEDVALUE(MetricSelector[Metric]),
    "Revenue", [Total Revenue],
    "Cost", [Total Cost],
    "Profit", [Total Profit],
    "Margin", [Profit Margin],
    BLANK()
)
```

### Dynamic Title

```dax
Dynamic Title =
VAR SelectedCountry =
    SELECTEDVALUE(
        Customers[Country],
        "All Countries"
    )

RETURN
    "Revenue Performance - " & SelectedCountry
```

### Cumulative Customer Count

```dax
Cumulative Customers =
VAR CurrentDate =
    MAX(Calendar[Date])

RETURN
    CALCULATE(
        DISTINCTCOUNT(Sales[Customer ID]),
        FILTER(
            ALL(Calendar[Date]),
            Calendar[Date] <= CurrentDate
        )
    )
```

Note: This calculates distinct customers across all dates up to the current date. It is not equivalent to a cumulative sum of monthly distinct customer counts.

### Year-over-Year with Missing Previous Period

```dax
Revenue YoY % =
VAR CurrentRevenue =
    [Total Revenue]

VAR PreviousRevenue =
    [Revenue Previous Year]

RETURN
    IF(
        NOT ISBLANK(PreviousRevenue),
        DIVIDE(
            CurrentRevenue - PreviousRevenue,
            PreviousRevenue
        )
    )
```

## 15. Blank & Error Handling

### ISBLANK()

```dax
Revenue Check =
IF(
    ISBLANK([Total Revenue]),
    "No Data",
    "Available"
)
```

### COALESCE()

```dax
Revenue Display =
COALESCE(
    [Total Revenue],
    0
)
```

### DIVIDE()

```dax
Profit Margin =
DIVIDE(
    [Total Profit],
    [Total Revenue],
    0
)
```

### IFERROR()

```dax
Safe Ratio =
IFERROR(
    [Total Revenue] / [Total Costs],
    BLANK()
)
```

### Important distinctions

- `BLANK()` is not the same as an empty string.
- `ISBLANK()` checks for blank values.
- `COALESCE()` returns the first non-blank expression.
- `DIVIDE()` handles division by zero.
- `IFERROR()` catches errors in an expression.
- Avoid replacing every blank with zero automatically: blanks can have important analytical meaning.

## 16. Performance Optimization

DAX performance depends on the data model, the formula and the query generated by Power BI.

### 1. Prefer measures over unnecessary calculated columns

Calculated columns increase model size because their values are stored.

### 2. Use variables

Avoid repeating expensive expressions.

```dax
Profit Margin =
VAR Revenue = [Total Revenue]
VAR Profit = [Total Profit]

RETURN
    DIVIDE(Profit, Revenue)
```

### 3. Prefer simple aggregations

Use `SUM()` instead of `SUMX()` when a direct column aggregation is sufficient.

### 4. Avoid unnecessary FILTER()

Prefer Boolean filter arguments in `CALCULATE()` when possible.

```dax
-- Prefer for simple conditions
Revenue High Value =
CALCULATE(
    [Total Revenue],
    Sales[Revenue] > 1000
)
```

Use `FILTER()` when the filtering logic requires row-by-row evaluation or more complex expressions.

### 5. Avoid excessive nested iterators

Nested `SUMX()`, `FILTER()` and `ADDCOLUMNS()` expressions can increase calculation complexity.

### 6. Optimize the data model

- Use a star schema.
- Prefer one-to-many relationships.
- Avoid unnecessary bidirectional filtering.
- Remove unused columns.
- Use appropriate data types.
- Reduce high-cardinality columns where possible.

### 7. Avoid unnecessary FORMAT()

`FORMAT()` converts values to text, which can prevent numeric sorting and further numerical calculations.

Prefer setting the measure's format in the Power BI model.

### 8. Use DAX Studio

DAX Studio helps analyze:
- Server timings.
- Query plans.
- Formula Engine (FE) operations.
- Storage Engine (SE) operations.
- VertiPaq storage.
- Query execution time.

### 9. Understand the engines

| Component | Role |
|---|---|
| Formula Engine | Evaluates DAX expressions and coordinates operations |
| Storage Engine | Retrieves and aggregates data from the model |
| VertiPaq | In-memory columnar storage engine |
| DirectQuery | Translates model queries into source queries |

### 10. Prefer simple model design

A well-designed semantic model often improves performance more than complicated DAX optimizations.

## 17. Debugging & Validation

### Test intermediate calculations

Create temporary measures to inspect individual components.

```dax
Debug Revenue =
    [Total Revenue]
```

### Inspect filter context

```dax
Selected Country =
    CONCATENATEX(
        VALUES(Customers[Country]),
        Customers[Country],
        ", "
    )
```

### Count visible rows

```dax
Visible Sales Rows =
    COUNTROWS(Sales)
```

### Check selected values

```dax
Selected Year =
    SELECTEDVALUE(
        Calendar[Year],
        -1
    )
```

### HASONEVALUE()

```dax
Single Country Selected =
    HASONEVALUE(Customers[Country])
```

### ISINSCOPE()

Useful for detecting the current hierarchy level in a visual.

```dax
Current Hierarchy Level =
SWITCH(
    TRUE(),
    ISINSCOPE(Products[Product Name]), "Product",
    ISINSCOPE(Products[Category]), "Category",
    "Total"
)
```

### Common debugging functions

| Function | Purpose |
|---|---|
| `ISBLANK()` | Check blank values |
| `ISERROR()` | Check errors |
| `HASONEVALUE()` | Check whether one distinct value exists |
| `SELECTEDVALUE()` | Return selected value or alternative |
| `ISINSCOPE()` | Check hierarchy level |
| `VALUES()` | Inspect visible distinct values |
| `COUNTROWS()` | Count rows in a table expression |

## 18. DAX vs Power Query M

DAX and Power Query M serve different purposes.

| Feature | DAX | Power Query M |
|---|---|---|
| Main purpose | Analytical calculations | Data extraction and transformation |
| Execution | Model/query evaluation | Data refresh |
| Typical use | KPIs, ratios, time intelligence | Cleaning, merging, shaping |
| Context | Row and filter context | Step-based transformations |
| Language | DAX | M |
| Output | Measures, columns, tables | Loaded or transformed data |

### Example: Cleaning data

**Power Query M**

```powerquery
Table.TransformColumns(
    Source,
    {
        {"Customer Name", Text.Trim, type text}
    }
)
```

**DAX**

```dax
Clean Customer Name =
    TRIM(Customers[Customer Name])
```

**Best practice:** Perform data cleaning and structural transformations in Power Query whenever possible. Use DAX primarily for calculations and analytical logic in the semantic model.

## 19. Recommended DAX Workflow

When developing a measure for a real Power BI project:

1. **Understand the business requirement:** Define the metric, expected result and business rules.
2. **Inspect the data model:** Identify fact tables, dimensions, relationships and cardinality.
3. **Define the calculation grain:** Determine whether the calculation is at transaction, customer, campaign or monthly level.
4. **Create base measures:** Start with simple aggregations such as revenue, cost and transaction count.
5. **Build advanced measures:** Use `CALCULATE()`, iterators and variables to implement business logic.
6. **Validate evaluation context:** Check how slicers, visual filters and relationships affect the calculation.
7. **Test edge cases:** Consider blanks, zero values, missing dates and duplicate records.
8. **Validate against source data:** Reconcile totals with SQL queries or trusted source reports.
9. **Optimize:** Review DAX Studio timings and model performance.
10. **Document:** Maintain a consistent naming convention and document complex business logic.
